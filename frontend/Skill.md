# Frontend Skill Guide — Weather-Aware Truck Routing

## 1. Purpose

Build a responsive React + Vite + TypeScript application that helps a user compare up to three route candidates for a truck trip, inspect weather at route checkpoints, and understand why a route is recommended.

This document is the implementation contract for the frontend. API endpoints listed below are the **proposed backend contract**; implement them in Django or adjust this document if the backend changes.

## 2. Product requirements

The user enters:
- Origin and destination.
- Departure date/time.
- Truck load weight in pounds.
- Checkpoint sampling interval: 10, 25, or 50 miles.
- Forecast offset/selection from 0–48 hours.

The application should:
- Request up to three distinct routes.
- Display routes, checkpoint locations, ETA, risk level, and route summaries.
- Display a weather risk corridor/heatmap and a forecast-time slider.
- Explain the recommended route and the ranking criteria.
- Clearly disclose unavailable forecast data and routing-provider limitations.

## 3. Required stack

- React
- Vite
- TypeScript
- React Router (if multiple pages are used)
- Tailwind CSS (or the project's selected styling system)
- Leaflet + React Leaflet
- TanStack Query for server-state caching, loading, and retry behavior
- Zod for client-side validation (optional but recommended)
- Vitest + React Testing Library

Do not place provider API keys in frontend environment variables. Calls to OpenRouteService and Nominatim should go through Django so keys, rate limits, and provider policy are handled on the server.

## 5. Frontend environment variables

Create `frontend/.env.example`:

```dotenv
# Keep this relative when frontend and backend share a public domain.
VITE_API_BASE_URL=/api

# Optional: only set this if the frontend uses a separately hosted API.
# VITE_API_BASE_URL=https://your-backend.example.com/api
```

Never add `OPENROUTESERVICE_API_KEY`, Django secrets, or database credentials to a `VITE_*` variable; Vite variables are bundled into client-side code.

## 6. Proposed API contract

Base path: `/api`

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health/` | Check backend availability |
| GET | `/geocoding/search/?q=...` | Search for a place/address via the backend geocoding adapter |
| POST | `/trips/` | Validate and create/analyze a trip |
| GET | `/trips/{trip_id}/` | Retrieve saved trip analysis |
| GET | `/trips/{trip_id}/routes/` | Retrieve route alternatives and route summaries |
| GET | `/trips/{trip_id}/checkpoints/` | Retrieve checkpoint weather and risk results |
| GET | `/trips/{trip_id}/forecast/?offset_hours=0` | Retrieve forecast values for a selected offset |
| POST | `/trips/{trip_id}/reanalyze/` | Re-fetch/recompute analysis when explicitly supported |
| GET | `/schema/` | OpenAPI schema if `drf-spectacular` is configured |
| GET | `/docs/` | Swagger UI if configured |

These are recommended endpoints, not automatically generated by creating Django apps. Implement URL patterns, serializers, views, and tests before relying on them.

### Example trip request

```json
{
  "origin": "Denver, CO",
  "destination": "Colorado Springs, CO",
  "departure_at": "2026-10-20T08:00:00Z",
  "load_weight_lb": 32000,
  "checkpoint_interval_miles": 25
}
```

### Suggested response shape

```json
{
  "trip_id": "trip_123",
  "recommended_route_id": "route_2",
  "routes": [
    {
      "id": "route_2",
      "distance_miles": 75.2,
      "duration_minutes": 85,
      "risk_summary": {
        "severe_miles": 0,
        "high_miles": 3.1,
        "average_risk": 0.42
      },
      "geometry": [],
      "checkpoints": []
    }
  ],
  "warnings": []
}
```

Use actual backend response types as the source of truth; this example is illustrative.

## 7. UI and behavior

### Trip form
- Validate required fields and positive load weight.
- Use explicit units in labels.
- Store departure time with timezone information.
- Show a pending state while analysis is running.
- Disable duplicate submissions while a request is in flight.

### Route map
- Use OpenStreetMap tiles with required attribution.
- Render each available route with a distinguishable line style.
- Show checkpoint markers colored by risk.
- Provide accessible details in a side panel/table; do not rely on color alone.
- Fit map bounds to returned route geometry.
- Avoid rendering fake/duplicate routes if fewer than three alternatives are returned.

### Route comparison
Show:
- Recommended status and explanation.
- Distance and ETA.
- Severe miles and high-risk miles.
- Average risk score and risk distribution.
- Warnings, missing forecast values, and route-provider limitations.

### Forecast slider
- Range: 0–48 hours relative to departure, unless the backend defines a different reference.
- Debounce slider-driven requests if they trigger API calls.
- Keep map selection and displayed checkpoint values synchronized.
- Clearly mark times outside the available forecast horizon.

## 8. Risk display rules

Use risk values returned by the backend as authoritative. Do not duplicate risk classification logic in the browser. The frontend may map risk values to labels and accessible colors:
- `LOW`
- `MODERATE`
- `HIGH`
- `SEVERE`
- `NO_TRAVEL`
- `UNKNOWN` for unavailable/incomplete weather

Never treat missing weather as `LOW`.

## 9. Error handling and performance

- Set request timeouts where supported.
- Handle HTTP 400 validation errors, 429 rate limits, 5xx provider failures, and network failures.
- Show a retry action only when retrying is safe.
- Cache stable trip results with TanStack Query.
- Avoid refetching geocoding on every keystroke; debounce and respect provider policy.
- Use stable React keys for routes and checkpoints.
- Keep map components isolated to reduce unnecessary rerenders.

## 10. Accessibility and responsive design

- Support keyboard operation for forms and controls.
- Give inputs visible labels and validation messages.
- Provide a text/table alternative to map-only information.
- Use sufficient contrast and icons/text in addition to risk colors.
- On narrow screens, stack the trip form, map, route cards, and checkpoint details.

## 11. Testing checklist

- Trip form rejects missing origin/destination and invalid load.
- API errors appear as helpful messages.
- One, two, or three routes render without duplication.
- No-travel and missing-weather states are visually distinct.
- Forecast slider updates selected-time values.
- Route recommendation explanation matches backend response.
- Components work on mobile and keyboard navigation.

## 12. Definition of done

- `npm run build` succeeds.
- Frontend can call the configured Django API.
- No secrets are shipped to the browser.
- Routes, checkpoints, forecast state, and risk summaries are synchronized.
- Loading, empty, error, and unavailable-data states are covered.
- README documents how to run and configure the frontend.
